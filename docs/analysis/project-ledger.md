## How to maintain this ledger

- Give each entry a stable ID. Keep IDs when wording changes; record material changes in the history.
- Separate user decisions, documented facts, proposals and validated stakeholder requirements.
- Cite the evidence behind a claim. Mark unverified features as unknown rather than absent.
- In the SRS, reference relevant ledger IDs and add priority, acceptance criteria and validation evidence. These notes are not approved SRS requirements.
- Use Member 1–7 until responsibilities are assigned to named members. Owners below follow the existing roadmap and remain working allocations.
- Preserve dataset attribution and label sourced, transformed and simulated data separately. Do not record confidential stakeholder responses in a public repository.

Statuses: **Recorded decision**, **Documentation reviewed**, **Proposed**, **Open**, **Validated**, **Superseded**. Validation requires actual evidence or review; discussion alone does not imply institutional approval.

## DATA-001 — Selected public dataset: OULAD

**Status:** Recorded decision; public documentation reviewed; original archive downloaded and ZIP integrity verified.  
**Selection evidence:** User requested that OULAD be stored as the project's data source.  
**Research recorded:** 6 October 2026.  
**Owner:** Member 6; Member 3 reviews mappings and academic rules.

**Dataset:** Open University Learning Analytics Dataset (OULAD), an anonymised dataset of courses, students and virtual learning environment interactions for seven selected modules. The source describes related CSV tables connected by identifiers. [Publisher overview](https://research.stem.open.ac.uk/ouanalyse/dataset/), [UCI catalogue and download](https://archive.ics.uci.edu/dataset/349/open+university+learning+analytics+dataset).

**Documentation:** [Publisher data dictionary](https://research.stem.open.ac.uk/ouanalyse/open-dataset-more/). Use the dictionary to interpret fields and joins rather than guessing from column names.

**License:** [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/), as stated in the publisher documentation and UCI catalogue. Credit the creators, link the source/license and identify modifications when redistributing or adapting data.

**Attribution:** Kuzilek, J., Hlosta, M., and Zdrahal, Z. (2017). *Open University Learning Analytics dataset*. Scientific Data, 4, 170171. [Research paper DOI](https://doi.org/10.1038/sdata.2017.171). UCI also supplies [dataset DOI 10.24432/C5KK69](https://doi.org/10.24432/C5KK69).

### Data relevant to our design

| Source table | Relevant information | Intended use / interpretation |
| --- | --- | --- |
| courses.csv | Module, presentation and duration | Course offering / academic period context |
| assessments.csv | Assessment ID, type, due-date offset and weight | Assessment definitions and comparison context |
| studentAssessment.csv | Student ID, assessment ID, score, submission offset and banked-result flag | Assessment performance and submission history |
| studentInfo.csv | Student/module/presentation association and final result; also demographic fields | Enrolment context and outcome; omit unrelated demographics from the initial prototype |
| studentRegistration.csv | Registration and withdrawal offsets | Interpret enrolment coverage and withdrawals |
| vle.csv | Online resource IDs and types | Optional engagement extension, outside the current core scope |
| studentVle.csv | Dated resource interactions and click totals | Optional online activity; never treat clicks as classroom attendance |

The publisher defines assessment scores on a 0–100 scale and dates as offsets from the presentation start. It documents banked results, missing submissions and exam-result availability. Preserve these meanings when transforming records; a missing result is not automatically zero. [Field definitions](https://research.stem.open.ac.uk/ouanalyse/open-dataset-more/).

### Fit, boundaries and unresolved mappings

- OULAD supplies assessment data suitable for a performance dashboard. Our use of it for this project is a design choice, not evidence that it represents our university or MCA cohort.
- It supplies online activity rather than classroom session attendance. Subject-wise attendance counts and denominators must come from separately labelled simulation or a later authorised source.
- Preserve identifiers and documented table relationships. Use module plus presentation for course context; do not combine different presentations as if they were one class.
- Confirm weighting, rounding, pass thresholds, banked-result handling and comparable progress measures. Do not adopt the source institution's academic rules as our university's policy.
- Keep sourced results and simulated additions distinguishable. Any attendance/performance relationship involving generated attendance is a demonstration, not a real empirical finding.
- Record source, transformation version and simulation provenance in the dataset design. The exact schema and user-visible provenance labels remain to be designed.
- No application import, curated subset or synthetic attendance generation has been completed at this stage.

**Local data record:** See the [OULAD source record](../../data/sources/oulad/README.md) and its download manifest for archive provenance and integrity information. The original archive contains seven CSV files and is 46,748,244 bytes. All ZIP entries passed CRC verification and all CSV headers were read. Data values, joins and completeness remain unaudited. The stored original archive is a reference copy; it is not the final demonstration fixture.

### SYS-001 — Moodle

**Status:** Documentation reviewed.  
**Sources:** [Gradebook documentation](https://docs.moodle.org/en/Grades), [Analytics documentation](https://docs.moodle.org/en/Analytics).

**Verified findings:** Moodle's gradebook brings together course grades and provides calculation, history, import and export facilities. Its analytics documentation describes models and indicators supporting learning-related insights.

**Design questions:** How should we organise assessments, expose calculations, support corrections and retain import/export consistency? Which analytics can be explained through simple agreed rules?

**Scope boundary:** Our study focuses on academic records and reporting; adopting Moodle's broader LMS or predictive models is not a current project requirement. The review extension verified documented session attendance through the Attendance plugin, distinct from default core functionality. [Attendance documentation](https://docs.moodle.org/503/en/Attendance_activity).

**SRS areas informed:** Marks management, import/export, calculation transparency, correction history and analytics definitions.

### SYS-002 — Canvas Course Analytics

**Status:** Documentation reviewed.  
**Source:** [Official Course Analytics guide](https://community.instructure.com/en/kb/articles/662739-what-is-course-analytics).

**Verified findings:** The guide documents grade charts/tables, individual and course comparisons, participation information, downloadable reports and student/instructor views. It also describes online attendance criteria and distinguishes activity measures such as page views and participation.

**Design questions:** Which chart/table combinations and filters help users compare student progress with a course? How should missing, late or excused work be shown?

**Scope boundary:** Online attendance and activity must not be equated with physical classroom attendance. Our attendance definition must be established independently.

**SRS areas informed:** Dashboard views, filters, comparisons, report outputs, role-based visibility and metric explanations.

### SYS-003 — Frappe Education

**Status:** Documentation reviewed.  
**Sources:** [Student portal](https://docs.frappe.io/education/student-portal), [Student attendance](https://docs.frappe.io/education/student-attendance), [Assessment results](https://docs.frappe.io/education/assessment_result).

**Verified findings:** The student portal presents grades and attendance alongside academic information. Separate documentation covers recording attendance and assessment results.

**Design questions:** How should student accounts link to academic records? How should assessment and attendance entry connect to student views and academic periods?

**Scope boundary:** Fees, admissions and other broader education-management functions are outside the initial dashboard scope. This is our scope decision, not a claim that Frappe lacks analytics.

**SRS areas informed:** Student-record associations, marks/attendance entry, academic context and student access.

### SYS-004 — OpenEMIS Core

**Status:** Documentation reviewed.  
**Sources:** [Product overview](https://www.openemis.org/products/core), [Institution statistics documentation](https://support.openemis.org/core/en/institution-statistics/).

**Verified findings:** OpenEMIS Core supports education information management. Its statistics documentation describes student absence reports, attendance summaries and marks-entry status reports.

**Design questions:** How should we present attendance totals/rates and distinguish incomplete academic records from poor performance? Which summaries are useful to faculty or coordinators?

**Scope boundary:** Our prototype addresses a bounded academic cohort rather than the broader institution/system-management scope described by the product.

**SRS areas informed:** Attendance summaries, completeness indicators, cohort reporting and reporting periods.
