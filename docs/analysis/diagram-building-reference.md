**Status:** working reference for role-feature review. Update the feature list and SRS after the role decisions are confirmed; this file does not authorise implementation.

## Drawing rules

**Coverage and readability.** The inventory remains at 22 diagrams: four each of use case, sequence and state, plus the existing context, DFD, activity, ER, class and component diagrams. CTX-01 and DFD-00 give breadth; the other locked models keep their existing scope. Each focused diagram owns only the behaviour named in its row. Do not draw a second focused diagram for the same feature. Class assignment submissions belong to UC-01; STATE-03 concerns self-reported academic work and achievements. A sequence may show authentication or data lookup as a prerequisite without taking ownership of the login or dashboard-view feature. A state diagram shows one object's lifecycle, not the full actor workflow. Use standard symbols, legible labels and whitespace. [UCSPEC-001](../diagrams/use-case-specifications.md) contains earlier scenarios and must be reconciled with this allocation before drawings are frozen.

**Notation.** Each use-case page names and draws all actors outside the system boundary, with separate associations to the cases they actually initiate or participate in. `<<include>>` points from a base case to behaviour that always occurs; `<<extend>>` points from conditional behaviour to its base case and labels the condition. For UC-04, label the manual/CSV account-creation conditions and make their choice exclusive. Do not add these links just to connect ovals. DFD arrows name data and external entities never connect directly to stores. Number Level 1 processes as 2.x and 3.x and balance their external flows with DFD-00. Each activity page draws the named swimlanes, places actions in their responsible lane and uses guards at decisions; a branch involving a second person must show the handoff. Sequence diagrams use ordered messages and `alt`/`opt` frames. State diagrams follow one named object, not screen navigation.

**Data and access.** Blank, missing, zero, absent, unreleased and stale are different states. Sessional 1/2 and the Teacher-selected sum or average remain distinct from quiz scores. An assigned Teacher edits only their subject and reads other released subject results for their assigned Students. HOD performs Teacher actions only for classes they are personally assigned to teach; department-wide viewing and assignment are separate HOD permissions. Admin account rights do not imply academic editing; programme/subject setup authority remains TBD. One attendance source is active per subject/section/term, and switching it must not double-count a session.

**ER and implementation boundary.** ER-01 is the agreed **conceptual core**, not proof that ten physical tables store every selected feature. Keep Student, Teacher, HOD and Admin separate; do not draw `UserAccount`, `Offering` or `TeachingEnrollment` as ER entities. Show Department offers Programme, Student enrols in Programme, Programme contains Subject, Teacher selects Attendance Source, and Marks/Attendance Record relate to the relevant Teacher-Subject-Student combination. Resolve the ternary relationship's SQL mapping and storage for quiz, work, feedback, calendar and notices during logical database design. FEAT-24 has no approved physical storage or real-response workflow.

**Rules still needing confirmation.** Assignment file limits, submission updates and late-work policy; monthly report cutoff, missing-data rule and retention; exact resume/profile fields and visibility; programme/subject setup authority; mark release/reopening authority; attendance codes and source switching; quiz attempts; work verification; feedback escalation; and several ER cardinalities are not institutionally confirmed. Mark the affected guard or relation **TBD** rather than completing the drawing with an invented rule. Personal monthly reports are derived from existing marks, attendance and quiz results; they do not create a new official grade.

**Role implementation.** HOD is a temporary appointment for an existing Teacher in the same department, using the Teacher's Auth identity. HOD access is checked on each request; when Admin replaces the appointment, the former HOD keeps Teacher access only. Teaching actions still require the Teacher's own class assignment. The HOD entity remains in the conceptual ER to show the appointment and its Department relationship.

### STATE-04 transition guide

The state machine follows **one quiz**, not one Student attempt. Use the following guards and leave individual attempt details inside the `open` state.

| Transition | Event and guard |
| --- | --- |
| Draft -> Configured | Assigned Teacher saves MCQ questions, answer keys, question count and timer. Missing/invalid configuration stays Draft. |
| Configured -> Validated | Dashboard checks question count, timer and assigned subject/group. Failed checks return to Configured with errors. |
| Validated -> Published | Assigned Teacher publishes for the chosen class. An unauthorised actor cannot change state. |
| Published -> Open | Availability time arrives. An unpublished or not-yet-open quiz rejects attempt starts. |
| Open -> Open | An enrolled Student starts, submits or times out on **their own attempt**. Duplicate submissions do not create a second score; other Students' attempts continue. |
| Open -> Closed | Availability ends. No new attempt starts; existing timed attempts follow the agreed deadline rule. |
| Closed -> Scoring -> Results available | Dashboard finishes and checks attempt scores, then applies the result-release rule. Scoring failure remains in Scoring for a safe retry. |

The exact availability window, attempt limit and result-release rule remain TBD; do not invent their values in the drawing.
